# 원고 본문의 원본은 저자 파일, Magus는 최신 업로드의 사본

- 날짜: 2026-10-06
- 결정: 사용자 결정 **#68**(status.md "확정 기록")
- 단계: P1 7단계(아버지 온보딩) 직전
- 관련: [reupload-design.md](reupload-design.md)(다시 올리기 설계안 초안), [store-interface.md](store-interface.md)(파일 우선 저장), [front-matter-boundary.md](front-matter-boundary.md)

## Problem

- P0 설계는 "단일 진실 원천 = 디스크의 `ch-NN.md`"였다. 원고가 두 파일로 갈라진 실제 사례를 막으려는 것이었다. Claude가 `book_write_chapter`로 장 단위로 고쳐 쓰는 것이 기본 흐름이었다.
- 그런데 저자(아버지)는 원고를 Word(·한글)에서 직접 쓰고 고친다. 원고 파일은 저자의 것이고 Magus 밖에 있다.
  - Claude가 Magus 안의 장을 고쳐 쓰면, Word 원고와 Magus 원고가 다시 두 갈래가 된다. 막으려던 문제가 그대로 돌아온다.
  - 저자가 Word에서 고친 내용은 Magus가 알 길이 없다. 다시 올려야만 들어온다.
- 제약
  - 도구 이름은 바꾸지 않는다(`book_*`). 서버 instructions의 규칙 문장은 원문 그대로 둔다(바꾸려면 사용자 승인).
  - 결정·영감·문헌은 원고 판이 바뀌어도 남아야 한다.

## Action

- **원고 본문의 원본은 저자의 Word(·한글) 파일이다. Magus의 원고(`ch-NN.md`)는 최신 업로드의 사본이다.**
- 예상 사용 흐름
  1. 저자는 원고를 Word에서 직접 고친다.
  2. 막히거나 표현 자문이 필요하면 Claude와 대화한다. Claude는 Magus로 책 전체 맥락(목차·결정·미해결·장 하나·검색)을 보고 조언한다.
  3. 떠오른 생각과 읽은 논문은 메모와 함께 Magus에 쌓는다(Casper·Melchior).
  4. 작업이 끝나 원고가 바뀌면 Magus에 다시 올린다.
- 따라서
  - Claude의 원고 수정안은 대화로 내고, 저자가 Word에 반영한다. Magus 안의 원고를 Claude가 직접 고쳐 쓰는 것은 기본 흐름이 아니다.
  - **다시 올리기가 핵심 기능이 된다.** 설계안은 [reupload-design.md](reupload-design.md)에 있다(미구현).
  - "원고 상태를 대화 밖에 저장한다"는 원칙은 유지한다. 목차·결정·미해결·판 이력은 여전히 Magus에 있다. 바뀌는 것은 "원고 본문의 원본"이 어디냐뿐이다.
  - "원본은 사람이 읽을 수 있는 파일, SQLite는 인덱스"라는 저장 원칙도 그대로다. Magus 안에서는 `ch-NN.md`가 인덱스의 원본이고, 그 `ch-NN.md`는 저자 파일의 사본이다.
- 비교한 대안
  - **Magus 원고가 원본(P0 그대로)**: 저자에게 Word를 버리고 Claude를 통해서만 고치라는 뜻이다. 저자의 실제 작업 방식과 맞지 않는다.
  - **양방향 동기화**(Magus에서 고친 것을 Word로 자동 반영): Word 서식·코멘트·그림을 보존하며 합치는 비용이 크고, 충돌을 저자가 풀어야 한다. 원고가 두 갈래가 되는 문제를 오히려 키운다.

## Result

- 문서에 반영했다: CLAUDE.md(개요·"왜 만드나" 5·절대 원칙·book_write_chapter·book_import), status.md(확정 기록 #68, 검토 대기 #69~#76), README "처음 쓰는 순서", store-interface.md 후속 메모.
- 코드는 바꾸지 않았다. 이 결정과 어긋나는 곳은 아래와 같고, 각각 검토 대기 결정으로 올렸다.
  - 서버 instructions 규칙 4("장을 고치면 book_write_chapter로 그 장만 저장")가 기본 흐름과 반대다(#74).
  - `book_import(replace=true)`는 프로젝트 전체를 휴지통으로 옮긴다. 다시 올리면 결정·직접 남긴 미해결·닫은 미해결이 활성 프로젝트에서 사라진다(설계안 6절, #76).
- 검증 방법: 다시 올리기를 구현할 때, 다시 올리기 전후로 결정·직접 남긴 미해결·책장 파일의 해시가 같은지 테스트로 고정한다(설계안 6절).

> 대안을 버린 이유: Magus를 원본으로 두면 저자의 작업 방식과 맞지 않고, 양방향 동기화는 비용이 크며 갈라짐을 키운다. 그래서 저자 파일을 원본으로 두고 다시 올리기로 맞춘다.
