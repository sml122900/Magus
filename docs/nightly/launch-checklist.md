- 코드·설정·서버는 건드리지 않았다. 저장소 문서·코드를 읽고, 가격은 2026-10-14에 웹에서 확인했다(출처는 맨 아래).
- **법률 자문이 아니다.** 3절은 무엇을 갖춰야 하는지 정리한 목록이다. 공개 가입 전에는 전문가에게 한 번 확인받는다.
- 표의 '출시 전': **필수** = 다음 사람을 받기 전 / **권장** = 10명이 넘기 전 / **나중** = 100명 또는 공개 가입 때.

## 한눈에

- 지금 구조는 '허용 목록 2명'에 맞춰져 있다. 10명 초대까지는 작은 일 몇 개면 된다. 공개 가입은 아직 이르다.
- 가장 큰 걸림돌은 셋이다.
  1. WorkOS **Staging은 약관상 실사용자용이 아니다**("not intended for customer-facing traffic per the Terms of Service"). 그래서 Production으로 옮겨야 한다.
  2. 개인정보처리방침과 문의 창구가 없다.
  3. 도움말 비용에 전체 상한이 없다. 사람마다 하루 30번만 막혀 있어서, 최악이면 한 사람이 한 달에 약 $40를 쓸 수 있다.

## 1. 가입 열기 방식

**지금 상태**
- 로그인: WorkOS AuthKit **Staging**(`dapper-palace-57-staging.authkit.app`). 가입은 끄고 초대만 받는다. 로그인 방법은 이메일 코드(Magic Auth)다(`docs/decisions/auth-provider.md`).
- 받는 사람: `deploy/.env`의 `ALLOWED_USERS="sub=user_id,…"`(`src/magus/auth.py: parse_allowed`).
  - 사람을 바꾸면 `docker compose up -d`로 컨테이너를 다시 만들어야 한다(`restart`는 .env를 다시 읽지 않는다, `docs/deploy.md` 2-1절).
  - 목록에 없는 사람은 403 화면에 본인 sub id가 보인다(`web.py` callback). 목록이 비면 모두 403이다.
- 데이터 폴더 이름(`data/users/<user_id>`)은 운영자가 직접 짓는다.
- 결정 #49: Staging은 공개 서비스로 바꿀 때까지만 쓴다. Staging에서 보낸 메일은 제목 앞에 `[STAGING]`이 붙는다.
- 환경 사이에 사용자를 옮기는 기능은 없다. Production에서는 다시 로그인해야 하고, 그러면 sub가 새로 생긴다.
  - Magus는 sub → user_id로 사람을 찾으므로, `ALLOWED_USERS`의 sub만 바꾸면 된다. 데이터 폴더는 그대로 쓴다.

| 방식 | 할 일 | 좋은 점 | 걸리는 점 | 출시 전 |
|---|---|---|---|---|
| **WorkOS Production 이전** | 새 issuer, 웹 클라이언트, 리소스 `…/mcp`, 리디렉션 3개, Magic Auth·가입 끔 설정. `.env`의 `AUTH_ISSUER`·`WEB_CLIENT_*`·`ALLOWED_USERS`(sub만) 바꿈. 두 사람 모두 커넥터를 지웠다가 다시 추가 | 약관을 지키고 `[STAGING]`이 없어진다 | 한 번 끊긴다. 10-05에 Production 생성이 거부됐던 문제를 먼저 확인해야 한다 | **필수** |
| A. 지금처럼(운영자 초대 + 허용 목록 수작업) | WorkOS에서 초대 → 첫 로그인 403 화면의 id → `.env` → `up -d` | 코드를 고치지 않는다 | 한 사람마다 재시작한다(몇 초 끊김, 도움말 하루 횟수도 0으로 돌아감) | 10명까지 가능 |
| B. 초대 코드 | 허용 목록을 파일(예: `data/allowed.json`)로 옮겨 재시작 없이 읽기. 코드를 넣으면 user_id를 자동으로 만들기 | 운영자는 코드만 보내면 된다 | 반나절~하루 작업, 코드 유출 관리 | 권장 |
| C. 대기 명단 | 신청 폼 + 운영자 승인 | 받는 속도를 조절할 수 있다 | B의 일에 폼·저장이 더해진다 | 나중 |
| D. 공개 가입 + 사람별 한도 | WorkOS 가입 켬, 403 대신 자동 등록 | 운영자가 손댈 일이 없다 | 먼저 2·3·5절(속도 제한·처리방침·탈퇴)이 있어야 한다 | 나중 |
| 메일 확인 | WorkOS 이메일 코드·Google 로그인이 메일 소유를 확인한다 | — | — | 이미 됨 |

**추천**: Production 이전(필수)을 하고 10명까지는 A로 간다. 10명이 넘기 전에 B(초대 코드 + 허용 목록 파일)를 만든다. D는 2·3·5절을 끝낸 뒤에 한다.

## 4. 비용 추정

**가정**
- 도움말 시스템 프롬프트 = 안내 문장 564자 + `docs/help/*.md` 다섯 개(지금 31,652자).
  - 10-09 측정값: 문서 15,120자였을 때 캐시 쓰기 15,749토큰(status.md 0-22절). 글자 하나가 대략 1토큰이다.
  - 그래서 지금은 **약 32,000토큰으로 추정**한다. 문서가 그사이 두 배가 됐다. 실제 값은 다음 도움말 로그 `help ok … cache_write=`로 확인한다.
- Haiku 4.5 가격: 입력 $1, 캐시 쓰기(5분) $1.25, 캐시 읽기 $0.10, 출력 $5(백만 토큰당). 캐시 최소 길이 4,096토큰은 넘는다.
  - 캐시 없이 묻기 ≈ 32k × $1.25 + 답 200토큰 × $5 + 질문 ≈ **$0.041**
  - 5분 안에 누군가 물은 뒤 묻기 ≈ **$0.0045**. 프롬프트가 모든 사람에게 같아서 캐시는 사람 사이에도 이어진다.
- 쓰임: 쓰는 사람 한 명이 하루 평균 1번 묻는다(한 달 30번).
  - 10명이면 캐시 없는 질문이 80%: 300번 → 약 $10.
  - 100명이면 캐시 없는 질문이 40%: 3,000번 → 약 $58.
- 상한: 한 사람이 매일 30번을, 모두 캐시 없이 묻고, 답이 600토큰이면 한 달 약 $40다.
- Haiku 5.5로 바꾸면: $0.10 / 캐시 쓰기 $0.125 / 캐시 읽기 $0.01 / $0.50. 같은 글이 토큰으로는 약 30% 늘어난다.
  - 캐시 없이 약 $0.0054, 캐시 있으면 약 $0.0006으로 **약 8분의 1**이다.
  - 다만 생각(thinking)이 기본으로 켜져 있어서 답 600토큰을 먹을 수 있다. 실패했을 때 대신 답하는 기능(fallback)도 없다. 코드를 고치고 시험해야 한다.
- 저장: 한 사람이 실제로 쓰는 양을 평균 100MB로 가정했다. 한도(1,000MB)까지 채우는 경우는 '최악'으로 따로 적었다.
- 서버는 1 vCPU·1GB이고, 평소 magus가 약 100~130MiB를 쓴다. 100명이면 동시에 몰리는 무거운 일 때문에 4GB를 권한다.

|---|---:|---:|---|
| 서버 Vultr | $5(`vc2-1c-1gb` 그대로: 1 vCPU·1GB·25GB) | $20(`vc2-2c-4gb`: 2 vCPU·4GB·80GB) | Vultr plans API |

## 7. 문의 창구

**지금 상태**: 없다.
- 403 화면에는 "허용 목록에 없습니다(403)"와 id만 나온다.
- MCP 403은 "운영자에게 문의하세요", 문서 바꾸기 실패는 "운영자에게 알려 주세요", 도움말 봇도 "운영자에게 알려 달라"고 말한다. 그런데 어디로 알리라는지 주소가 없다.

**추천**
- 문의 전용 주소 하나(예: `help@lifebookapplication.com`)를 만든다. 도메인 DNS가 Cloudflare에 있으면 Email Routing(무료)으로 운영자 메일에 전달할 수 있다. 다른 서비스와 같은 도메인이면 주소 이름을 정해야 한다.
- 보일 곳: 로그인 화면 아래, 403 화면, 내 정보(`/me`), 처리방침의 보호책임자 연락처, `docs/help/04-limits.md`(도움말 봇이 안내할 수 있게).
- 답할 목표 시간(예: 2영업일)을 함께 적는다.
- 폼은 나중에 만든다. 스팸 처리와 저장 부담이 생긴다.
- 출시 전: **필수**. 처리방침에 연락처가 있어야 한다.
